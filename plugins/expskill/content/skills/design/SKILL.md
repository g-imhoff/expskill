# Design

## Ground

Use this phase when the user explicitly invokes `$design`. Also run direct Design when an explicitly invoked `$use-expskill` deliberately selects it for accepted UI work whose technical planning is already accepted. That selection runs in the invoking conversation with the default `direct` invocation mode and requires no second invocation or CLI launch. When both planning and UI approval remain unresolved, the user instead opens the isolated Design CLI conversation beside Plan under the router's parallel protocol, with an exact baseline and helper-owned worktree. The router never starts those parallel CLI conversations. Both modes require the confirmed brief, technical gates, and explicit approval of the exact candidate. It applies to UI work of any size and stops at a route-neutral completed bundle. It does not integrate a feature or select another phase. Inspect the repository, branch/worktree, baseline, dirty state, framework, target seam, adjacent active components, primitives/tokens, content and localization patterns, tests, tool commands, and available isolated specimen capability before writing. Preserve unrelated work. Bind the UI contract, scope ledger, exclusions, baseline, and dirty fingerprint with the resolved Design state helper described under Rules and recovery. Before writing, declare `scope.owned_paths` as exact relative production, specimen, and evidence files. No directory, wildcard, traversal, or symlink ownership. The helper snapshots unrelated Git-visible file bytes and permits only declared owned edits. Owned paths are frozen for that session. A changed scope needs explicit approval and a reconciled new session, never a silent fingerprint refresh. Legacy sessions without an owned path declaration remain strict and must be reconciled before writes. Confirm and record a concise Design brief before writing. The brief is the canonical decision record: objective, requirements, compact/intermediate/wide expectations, non-goals, and its digest-bound Plan Graph, existing specification, or private immutable accepted-input source. For direct accepted input, use source kind `accepted-input` with its absolute private read-only path, byte digest, and original `decision_reference`. It preserves all accepted criteria and non-goals without requiring a Brainstorm-created file. Every consequential choice, including rejected directions and why they lost, belongs in the brief or a bound approval. A later phase works from the brief digest plus approvals with no re-asking. Project convention and confirmed intent outrank heuristics. Activated normative obligations outrank both, and genuine conflicts are surfaced. Derive production components, temporary specimen files, allowed dependencies, relevant rules, and actual pressure from content, state, and responsive conditions in the project.

## Choose

When evidence implies one structure, build it directly. If consequential structural ambiguity remains, render two or three lightweight structural probes and let the user select or correct the direction. A component/template seed requires explicit permission for its exact source, version, adaptation, dependency, provenance, and license consequences. A changed seed requires renewed permission.

## Build

Create production-intended components, interfaces, variants, states, styles, component-owned accessibility behavior, and relevant component tests within the scope ledger. Reuse active primitives/tokens. Record justified local values. Shared token or scope change requires explicit confirmation. Keep `specimen/scenario -> production component -> project primitives`: production code never imports gallery, fixture, mock, or scenario modules. Use deterministic synthetic schema-shaped content. The specimen has no external network, no external assets, no customer data, no credentials, no backend, no application state, no navigation, or live side effects. No silent installs or external side effects beyond an authorized hosted preview below. A smallest temporary specimen adapter may be used when project capabilities permit. Use the existing native stack and its isolated component capability. Do not introduce React, Vite, or another framework only to satisfy a preview host. If no safe native specimen can render, stop blocked with that local capability gap.

In routed mode, work only from the isolated worktree and the project's own
tracked files plus the explicitly supplied private read-only accepted input. A ready `.expskill/setup-design.md` record may be consulted
for the established sketch method, but it is never a prerequisite and its
absence never blocks routed Design. Keep new specimens and evidence inside that
worktree. Return questions to the router and do not ask the user directly. Each return names the Design workflow ID/revision, input digest, status, stable question ID, and exact decision needed. Resume only with its bound answer. A replacement owner loads and revalidates the same canonical workflow and accepted decisions, never starts a competing writer. The
router serializes Plan and Design questions. A stale baseline blocks the session. In routed mode only, create one coherent local commit as described under Deliver, direct invocation works without creating a candidate commit.

## Review

Maintain one stable isolated component surface. Render the same variant, state, representative synthetic content, theme, and data at actual compact, intermediate, and wide widths. Never use CSS zoom. Show applicable responsive, overflow, interaction, focus, loading, empty, error, partial, success, disabled, read-only, destructive, localization, long-content, input, motion, and permission pressure. Interactive panes remain live but only the selected pane is keyboard/accessibility-tree active. Announce width switches and reset the declared start state. Show directly dependent component families together.

In routed mode, create the initial coherent local candidate commit directly above the frozen baseline, or amend that one commit after a correction, and checkpoint before recording checks or requesting approval. Keep the candidate worktree clean for the checkpoint. Then run blocking gates against the exact checkpointed candidate before any approval request: project format, lint, type, and build checks. Runtime and console health. Declared interaction, keyboard, and focus paths. Reduced-motion behavior. Zero serious or critical accessibility findings. Zero page-level overflow at compact, intermediate, and wide conditions. Record a tooling gate as not applicable only when the project truly has no such tool and bind the inspected reason. Automated checks remain partial evidence, so retain the relevant manual observations too. Run repeatable local commands through the resolved helper's `record-check` operation with literal argv and the exact candidate inventory. The helper executes without a shell, retains command output, hashes it, and binds its receipt to the workflow, candidate files, baseline, brief, and contract. Carry its `record_id` in each technical result. A generic passing command does not establish an unrelated gate. Map each gate to the relevant recorded check and retain manual observations as labeled attestations. Technical evidence stays bound to the candidate.

Any failed gate is correction input. Do not present a technically failed candidate as a normal visual approval option: retain the failed evidence, repair the candidate, and rerun the affected gate plus dependent gates. If an unrelated project baseline or unavailable infrastructure prevents valid proof, stop blocked with the exact failure instead of weakening the gate. Once all gates pass, present every required state and viewport, the material change, trade-offs, unavailable later proof, and one decision. Approval binds the exact code/content digest, contract, rendered states, widths/themes, dependencies, and technical evidence. Material changes stale only affected components and dependents.

## Share the preview

Use the project's native stack for the isolated specimen. After local gates pass, prefer a hosted preview when publication is authorized, the host supports the existing bundle, and its tooling and authentication are available. Use Yodea for a compatible Vite React TS specimen and read [the Yodea preview reference](references/yodea-preview.md) before publishing. Upload synthetic fixture content only. Do not install tools, request credentials, add a framework, or change component architecture merely to obtain a hosted link.

If publication is forbidden, unavailable, incompatible with the native stack, or fails, retain the exact failure and continue with the working local specimen. This completes local Design delivery when the same candidate can be rendered and approved locally. It does not complete a separately requested hosted-publication obligation. If the user explicitly required a working hosted preview, that obligation remains blocked until resolved. A local-only mode requires no additional concept confirmation.

Record `preview_mode` as `hosted` or `local` in the manifest's review note. For hosted mode, include the verified URL, bundle digest, project label, and represented candidate revision or digest. For local mode, include the specimen entry path, exact launch command, required local capability, artifact digest, represented candidate identity, and the hosting limitation. Check that the selected review surface actually loads the candidate. The surface check is convenience evidence and does not replace technical gates. A material change stales affected evidence and approval. Never invent a URL or present an older preview as current.

Include the available hosted link or local review entry and limitation in each visual approval request, preview update, Design summary, downstream handoff, and any authorized PR description. In routed mode, relay it through the router. Keep hosted previews available through handoff and PR review under the reference's retention rules. For local mode, retain the specimen and reproducible launch recipe through handoff and PR review, or transfer the exact artifacts before removing the worktree.

## Deliver

The helper requires a confirmed brief before approval and delivery. Record questions with `id`, `material`, `resolved`, and `decision_reference`. A material question remains open until an explicit decision resolves it. Legacy question IDs remain unresolved until reconciled. Explicit `eligible=false` blocks delivery. Deliver only when every retained component is current, eligible, technically passing, user-approved, dependency-coherent, and free of unresolved decisions, and its hosted or local native preview is available for review. Each component declares an exact `files` inventory containing every production file it owns, including styles, exports, tests, and assets. Each entry has a relative path, byte digest, and `component` classification. Its `code_digest` is the canonical digest of `{"files": <entries sorted by path>}`, calculated by `design_state.component_digest`. Evidence and approval bind that aggregate digest. The candidate inventory must equal the complete union of all component inventories, with shared paths carrying identical entries. Legacy scalar component records require reconciliation before delivery. Bind three layers: candidate payload (components, exports, tests, assets), temporary preview and review evidence (specimens, fixtures, renders, results, approvals), and a route-neutral manifest (revisions/digests, classifications, contracts, assumptions, non-goals, rule decisions, exceptions, and integration obligations). The helper hashes every real candidate, review, and manifest file and rejects missing files, changed bytes, symlinks, or unrecorded command claims. Evidence, approval, and delivery bind the confirmed Design brief digest. Each approval includes `provenance` with kind `trusted-attestation`, actor `human` or `authorized-agent`, the existing authority reference, and the explicit decision reference. The helper checks this binding and provenance shape. It cannot authenticate a human identity, judge command relevance, or prove that a manual observation was accurate. Legacy evidence needs reconciliation and rerun checks before delivery. Keep temporary evidence private except for an authorized published synthetic specimen and its shared link, and do not retain workflow documentation merely because Design ran. Direct invocation preserves unrelated work, returns the delivered summary and stable review entry point without creating a candidate commit, then stops. When the workflow finishes, give the user the file path to the written Design Brief so they can find and reuse it. That summary names the confirmed brief digest, the approval digests, and the consequential decisions so the next phase inherits the complete context with no re-asking. In routed mode, relay the review entry through the router as above. Use this order for both the initial candidate and corrections: create or amend the single local commit, checkpoint it, record replacement checks, present the exact candidate, obtain its explicit approval, persist the current bindings, then deliver. A changed checkpoint clears superseded components, evidence, and approvals while retaining the confirmed brief, decisions, and invalidation references. Any genuine candidate change requires fresh byte-bound evidence and approval after that checkpoint. Never amend after approval and then treat the erased approval as current. Routed invocation returns the candidate-bearing delivery receipt and manifest to the router, then stops without integration.

## Rules and recovery

Read `references/rules-index.md` first. For a narrow component with a small, bounded concern set, selectively load the applicable category references. For a complex composite with interacting regions, state families, density, breakpoint composition, or several behavior modes, load the complete category catalog before shaping it. When classification is uncertain, choose the broader relevant load and revisit it after the first isolated render. This is an evidence-loading strategy, not a fixed ruleset, viewport system, or state matrix. Project convention and activated obligations still decide which loaded rules apply. Activated normative rules bind only when their platform, level, trigger, and exceptions hold, surface any conflict.

Resolve `../../scripts/design_state.py` relative to the loaded Design skill directory, then use that absolute helper path from the target worktree. In this source checkout its locator is `plugins/expskill/content/scripts/design_state.py`. Neither locator is relative to the target project, and a project-local `scripts/design_state.py` is not the packaged helper. Its normal root is `$XDG_STATE_HOME/expskill/design` (or the platform XDG default), while an explicit state home is test/API-only. It is the only state writer and uses expected-revision compare-and-swap. Initialize direct use with the default `direct` invocation mode. Initialize an isolated session the user opened with `invocation_mode` set to `routed`. The helper refuses candidate checkpoints in direct mode and requires one before routed delivery. On missing direction return `not-ready`. On missing specimen capability return `blocked`. On unsafe workspace or contract conflict stop and present the smallest decision. Never infer approval, silently broaden scope, or route downstream.

The Design CLI takes one operation name and reads its JSON object from standard input. Use `<Python 3 executable> -B <absolute helper path> --help` to list operations, then `<Python 3 executable> -B <absolute helper path> <operation> < <private payload file>`. Never pass the JSON object as a positional argument. For `discover`, the input object contains `repository` and `branch`. Other operations use their public API argument names. The optional `--state-home <root>` follows the operation and is only for isolated tests. Plan has a separate CLI with its own flags, so do not transfer Design's argument convention to it. Preserve stdout as the actual operation receipt and retain stderr and exit status on failure.

A delivered workflow is immutable history, including its original candidate-bearing receipt for a Plan join. Load it by workflow ID to inspect the historical snapshot without claiming that the current checkout still represents it. Discovery selects only active or paused owners. Start a successor on the same repository and branch only after its previous owner has delivered or was explicitly discarded. Keep delivered records and receipts, and never resume, discard, or rewrite them to make room.

After an interruption between the Git commit and its checkpoint, discover the active workflow to recover its ID and revision, verify the frozen baseline and the clean single-commit candidate, then call `checkpoint-candidate` with the actual HEAD before normal loading. The checkpoint revalidates those facts and retains accepted intent while clearing superseded bindings. After a completed checkpoint, load that same workflow and resume from its saved revision. Rerun any check whose receipt was lost, and obtain fresh approval when no current bound decision was saved. Do not use predecessor recovery to undo a legitimate candidate amendment. Predecessor recovery is for a torn workflow generation stored outside the checkout that still revalidates against the current candidate. Never initialize a replacement workflow to reset approvals or bypass its active owner.
