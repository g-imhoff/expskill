# Plan

## Boundary

`$plan` is a standalone, concept-read-only and source-read-only planning skill
that the user can also run as one direct CLI conversation beside Design.
The router relays its questions. Accept a
completed Concept Brief, a complete accepted specification, or another sufficiently concrete direction supplied directly. In parallel mode, accept the same immutable complete input locator and digest as Design. Preserve every accepted criterion and non-goal without requiring a Brainstorm-created file. Preserve
settled conceptual decisions. Technical evidence may expose a contradiction,
but planning must not repeat brainstorm, simulate brainstorm, or silently
redesign the concept.

Return `not-ready` for a vague direction. Do not route, invoke, open, select, or recommend another lifecycle skill, and do not begin production or test implementation, review, verification, integration, or GitHub delivery. Plan writes no production code, tests, executable configuration, or repository planning document. Its only writes are private graph operations through the helper, private research accounting through `../../scripts/research_budget.py`, and the one confirmed branch operation defined below.

## Workflow

Follow this order:

1. Inspect branch policy, the exact repository revision, and relevant uncommitted work. Resolve protection from repository instructions, authoritative hosted policy when available, and remote/default-branch metadata. Use common protected names only as a conservative fallback. The live integration target must be a non-protected workflow branch. If HEAD is protected or detached, propose one collision-free new local non-protected branch and its exact starting commit, explain how dirty work is treated, and wait for explicit user confirmation. Creating and switching to that branch after confirmation is the only repository Git mutation allowed to plan. Never overwrite a branch or commit, push, merge, rebase, stash, reset, delete a branch, or create a task worktree.
2. Once the branch is eligible, create or resume its canonical graph. Record every inherited Concept Brief decision and boundary as a graph decision with its evidence, rejected alternatives, and confirmation state. Keep settled conceptual decisions distinct from repository facts and proposed mechanisms. A pasted Concept Brief arrives settled. Do not re-ask what it already answers.
3. The main agent grounds the direction in the code before shaping the plan. Start at the likely implementation seam, then follow only relevant callers, state and effects, interfaces and consumers, dependencies, configuration, tests, runtime constraints, and history. Local grounding is never delegated and does not require confirmation. Before asking anything factual, exhaust supplied context, repository evidence, prior accepted evidence, and authoritative sources. Ask exactly one focused question per turn only for a material user-owned decision, preference, authorization, or confirmation. Use an explicit safe inference for routine reversible details.
4. Classify feasibility as feasible, conditionally feasible, contradicted, or not assessable. When code contradicts an accepted concept, cite the exact evidence and consequence, propose the smallest necessary amendment, and require approval instead of reopening broad ideation.
5. Create the adaptive minimum after the first grounding pass: one outcome, one grounded work slice or leaf task, and one proof obligation. Expand only for material decisions, boundaries, dependencies, consequences, or proof. Do not manufacture hierarchy, research, concurrency, rollback, or specialized lenses.
6. Show a concise current technical reality orientation: the existing shape, the important gap or constraint, and its planning consequence. This is context, not a confirmation gate.
7. Resolve remaining technical uncertainty. Load the existing private workflow research ledger across phases, including earlier Brainstorm or Grill Me exploration, using its returned locator and original identity. Reopening restores capacity, it never initializes a phase pool. A named external lookup performed directly by the coordinator consumes one research turn too, while required local code grounding remains autonomous phase work. Before the first research dispatch, record a run ID and the inherited research allowance or a standalone default of six researcher turns, at most three in flight, and twenty minutes of active research. Follow-ups, retries, replacements, and corrective researcher turns all consume it. Persist dispatch IDs, spent/outstanding turns, active intervals, and remaining allowance through the research helper. Carry its locator, original run identity, revision, limit source, and outstanding dispatch IDs on every pause, resume, replacement, or upstream return. Count overlapping active intervals once and exclude time waiting only for the user. Every research return, including blocked or interrupted work, reports dispatch ID, used turns, timing, and outstanding work. Reconcile unique dispatch IDs once. At exhaustion preserve credible evidence, stop launches, and block only the decisions missing material coverage. A named authorized extension changes the limit while retaining spent totals, never resets them. This is coordinator accounting unless the host independently enforces the same scope. Use a targeted official or primary lookup when the mechanism and source family are already selected. Use broad research only when meaningful alternatives or consequential uncertainty remain: one to three independent GPT-5.6-Luna researchers at max reasoning on named distinct questions, scaling the count to the ambiguity, with no repository access, preferred answer, sibling output, edit authority, user interaction, or planning role. Reuse sufficient accepted evidence with zero lanes. Add at most one targeted follow-up for one unresolved decision-relevant conflict or gap within the cumulative run budget. The main agent reconciles findings with repository truth, then resolves an isolated consequential choice with the user. For several connected user-owned choices, offer the `$grill-me` skill and invoke it only after explicit consent. Resume from its confirmed decision delta. Preserve rejected alternatives and their evidence-based reasons.
8. Build the complete implementation-facing graph. Connect outcomes, material evidence and decisions, slices, optional independently ownable leaf tasks, explicit joins, proof obligations, user projections, and the logical Git topology. Attach tests and proof to the behavior they validate. Classify work as `serial`, `parallel-candidate`, or `parallel-safe`. Prove stable inputs, ownership, isolation, independent proof, and a join before calling work parallel-safe. Make one cheap concurrency pass and stop when extra analysis would save little. Never spend more effort proving parallelism than it is expected to save.
9. Run deterministic structural validation and a brief main-agent semantic coverage closure. Classify scope from consequential coordinated changes across material behavior or ownership boundaries. Record broad scope as `audit.breadth` and high consequence as `audit.high_consequence`, with the concrete reason in `audit.reason`. These are coordinator scope attestations. A settled tiny serial plan does not become broad merely by citing an external source or retaining a selected and rejected alternative. Parallel work and required integration or Design joins impose their structural complexity floor, and declared audit requirements cannot later be lowered. For broad, complex, or high-consequence plans, run one initial bounded independent adversarial audit in a fresh read-only conversation with no inherited planner history, preferred verdict, or sibling output. Give the auditor the complete accepted input locator and digest, frozen graph locator and digest, workflow/revision, exact baseline, and relevant source boundaries so it independently checks omissions and unsupported claims. Wait for all research returns before dispatching it, keep the graph unchanged during its inspection, and reject a result bound to different inputs or pins. Reserve one initial five-minute auditor call and at most two fresh five-minute correction checks within the inherited lifecycle allowance. The standalone default is three calls and fifteen minutes in total. A correction check requires an actually corrected canonical graph and a fresh read-only conversation with the original accepted input, current frozen graph, and every retained unresolved finding. It covers a retained finding repair or a confirmed user correction within the existing accepted boundaries. Broader scope requires an explicitly named user-authorized extension that retains the original allowance history. Retain every spent and outstanding call, including failed, interrupted, missing, and stale results. There is no speculative retry or replacement, and no budget reset on correction or replacement. Never attest that a correction was independently checked unless that fresh check actually inspected its frozen graph. If the remaining inherited allowance cannot cover a required check, return not-ready instead of weakening the audit. Record its unique dispatch ID, actual actor/session identity, elapsed time, output locator/digest, findings, and used/outstanding/remaining accounting. The auditor may find concrete omissions or unsupported claims but may not research, redesign, edit, question the user, approve the plan, or delegate. Never certify your own audit as independent. If the required call cannot run or returns missing or stale evidence, keep the gate not-ready with the exact missing evidence. Tiny plans receive no audit ceremony.
10. Only after the backend graph is complete, derive concise progressive user projections in dependency order. The user never sees YAML. Present one coherent part per turn, include every material decision in plain language, and ask the user to confirm or correct its meaning. Each projection binds the decision versions it covers, so the confirmed graph carries the complete decision record forward. On correction, update canonical meaning first, explain the affected subgraph, invalidate and regenerate only affected evidence, decisions, work, proof, and projections, and preserve unrelated confirmations. Wording-only clarification is non-material. Derive `ready` automatically when every current part is confirmed and all invariants pass. Ask no redundant final confirmation. `ready` means every material decision lives in the graph with evidence and a current confirmation.

In routed parallel mode, work from the exact target checkout and baseline the
user hands you. The router never starts you and you never run inside it.
Remain the only Plan Graph writer. Return user questions to the
router instead of asking them directly. Every return names the Plan workflow ID/revision, accepted input digest, status, stable pending question ID, and exact decision needed. Include each research or auditor dispatch ID, actual actor/session identity, frozen baseline and graph pins, output locator/digest, findings or blocked status, inherited run ID and limit source, and spent, outstanding, and remaining allowance. The router reconciles those unique dispatch IDs into its existing run accounting before another phase launch. Resume only with the answer bound to that question and owner, or the digest-bound Design result sent to the same session. On replacement after interruption, load and revalidate the existing canonical graph and retained decisions before continuing, never initialize another competing writer or replenish research or auditor capacity. Mark the optional typed Design join as
required when production UI approval is part of the accepted outcome. The graph
must remain `not-ready` while that receipt is absent or stale. When the
router relays the Design conversation result, verify its frozen baseline, isolated
branch, one-commit candidate, Design workflow revision, confirmed brief digest,
approval digest, and manifest digest against the unchanged candidate-bearing
Design delivery receipt. Require its delivered lifecycle and require the
isolated branch tip to remain the exact candidate commit until integration.
After the exact candidate becomes an ancestor of the target HEAD, validate
that integrated ancestry so accepted cleanup may remove the isolated branch. Record it only
through the packaged helper's typed Design-join operation. Do not read or write
the Design state directly. A malformed, failed, unapproved, or stale result
stops the join.

## Canonical private graph

The deterministic helper is the only graph writer. Resolve it relative to the loaded skill package at `../../scripts/plan_graph.py`. Its source-package path is `plugins/expskill/content/scripts/plan_graph.py`. Use its dependency-free API or CLI for initialize, discover, load, apply, recover, pause, resume, discard, confirmed branch creation, accepted-basis freezing, and terminal completion. Before a later authorized owner begins production edits, `freeze_acceptance_basis` or `freeze-acceptance` preserves the complete ready planning graph outside rotating generations in the private `acceptance-bases` namespace. Keep its original locator, byte digest, workflow/revision, and baseline as the criterion basis while the canonical graph receives execution updates. Freezing is write-once through the helper and does not authenticate user assent or the claimed timing of a first edit. A user-approved material change may be reconfirmed in the same active workflow for a separate implementation epoch. `freeze_acceptance_epoch` or `freeze-acceptance-epoch` binds the prior snapshot locator and digest, current ready revision, and explicit new-run reason. It requires changed covered meaning and later typed projection approval, preserves a distinct revision-and-digest snapshot, and leaves prior actor criteria unchanged. Evidence freshness and execution rotations alone cannot create a new epoch. Omit `--state-home` in normal use so it owns a private XDG state root. Explicit roots exist only for isolated tests.

Research accounting is a separate permitted private write through `../../scripts/research_budget.py`, whose source-package path is `plugins/expskill/content/scripts/research_budget.py`. Use `initialize`, `discover`, `load`, and revision-bound `apply` through its API or CLI. Normal initialization omits `--state-home` and returns the absolute locator under the private XDG state root's `expskill/research-budgets` namespace. Repository identity is the resolved Git common directory, initial research branch or accepted research scope, and original run ID. Read-only research may use `main`, another protected current branch, or a supplied accepted branch without creating or switching Git state. A detached checkout may use `detached/<initial commit>` with the complete commit hash as its stable research scope. Changing phase, checkout, target branch, or clarified concept never rekeys an existing ledger. An inherited non-repository ledger retains its original accepted initial scope digest and run ID instead. For a fresh standalone Plan use its graph workflow ID as the run ID. If the inherited locator was lost, run `discover --repo <current checkout>` in the default namespace before initializing. It lists active pools for this canonical Git common directory across initial branches, with their original identity, spent turns, outstanding work, and remaining allowance. A known original run ID may filter discovery. Load a uniquely attributable pool using its returned locator and original branch, even after `main` becomes a workflow branch. An ambiguous result blocks new research and new initialization until existing run evidence resolves the identity. An absent result permits initialization only for a genuinely fresh run, it does not authorize resetting previously reported research. If an existing identity or state cannot be recovered, stop new research and retain the graph rather than resetting the allowance.

Before each direct investigation, researcher turn, retry, follow-up, or replacement, `apply` a `reserve` with a new unique `dispatch_id` and named `question`, then launch only after its receipt succeeds. Each reservation consumes one turn and one outstanding slot immediately, even if later cancelled. An uncertain interruption uses `interrupt` for that dispatch ID and retains its open interval and slot. Reconcile each return once with `reconcile`, its `dispatch_id`, `outcome` of `completed`, `failed`, or `cancelled`, and an `evidence_reference`. A repeated identical return changes no totals, a conflicting return stops reconciliation. An optional attested `ended_at_ms` may close work that ended before a delayed handoff. Use `activity-start` and `activity-stop` around coordinator research and reconciliation, closing coordinator activity before waiting only for the user. Dispatch and coordinator intervals overlap only once. Unknown outstanding work remains active conservatively until reconciled, even across a crash. Load before further launches, recheck remaining turns, active seconds, and slots, and retain the initial limit source. A named authorized `extend` supplies new bounded `limits` and an `authorization_reference` while preserving every reservation and prior interval. Use `close` with a `completion_reference` only when the entire owning research run has ended and no activity remains, never at a phase handoff or interruption. Closure retains spent totals and prevents reopening capacity, while discovery excludes the closed pool. Catalog and identity locks, strict identity checks, and atomic revisions protect these recorded totals. Launches, end times, source choices, and extension authority remain coordinator attestations, the helper does not authenticate people, monitor external agents, or prove agent compliance.

The graph is strict JSON-compatible YAML private state outside the repository. It permits one active graph per canonical repository identity and target branch, binds an opaque workflow ID, exact repository baseline, dirty-state fingerprint, and monotonic graph revision, and derives lifecycle state rather than trusting an edited status. It records outcomes, evidence, decisions, work, proof, Git topology, delivery state, and user projections without storing secrets, source copies, transcripts, or unbounded output.

Retain each projection's exact user-facing wording in its `presentation`. Use `issue_projection_presentation(graph=..., projection_id=..., text=...)` to bind that wording to its text digest and the current covered graph meaning, then store it with `regenerate-projection`, presented and awaiting confirmation. Prepare its current decision-version bindings before computing the presentation. Confirm only that unchanged presentation through `reconfirm-projection` after the user's answer. An initialization template may supply the exact previously approved wording as a plain `presentation` string. Legacy states without retained wording remain awaiting-user until the current meaning is presented and confirmed. Never invent the lost words or carry their old confirmation forward.

After the user's answer confirms a fresh material decision for the first time, call `issue_decision_confirmation(graph=..., decision_id=..., projection_id=...)` for the current presented projection covering that decision. Store its returned decision through `confirm-decision` with a typed operation receipt. This binds confirmation to the current decision version and retains the exact presented wording and digests. The helper records the coordinator's user-answer attestation, not independently authenticated assent. Do not invalidate an unchanged fresh decision to obtain a confirmation path. For a changed stale decision with retained confirmation, use the same issuer and `reconfirm-decision` after presenting and confirming its current meaning. Existing approved legacy decisions remain readable without inventing historical wording.

Technical work or repository-source changes require checking affected decision dependencies. The helper retains unchanged choices, decision versions, and their approvals while `revalidation_required` blocks readiness. Refresh stale repository evidence first. If the chosen meaning still holds, explicitly classify the dependency check as `unchanged-meaning` and call `issue_decision_revalidation(graph=..., decision_id=..., classification="unchanged-meaning", reason=...)`. Store the returned decision through `revalidate-decision` with its operation receipt. This records a `coordinator-attestation` bound to current dependency records and accepted source fingerprints. Matching canonical choice digests do not establish semantic compatibility with changed work. A changed choice requires a canonical decision edit and renewed user confirmation. Refresh stale planned or executed proof through its appropriate typed operation. Retained projection approval survives observation-only source changes, while changed facts, technical meaning, and explicit invalidation targets require their usual re-presentation and confirmation.

New presentations carry `source_digest_version: 2`, which treats repository revision as observation metadata. Unversioned legacy presentations retain their original revision binding and accepted wording. If refreshed repository revision makes that legacy binding stale, re-present the current meaning through the normal typed operations. Do not rewrite the old accepted digest or infer fresh assent during migration.

For a wording-only correction to a current confirmed projection, explicitly classify it as `unchanged-meaning` and call `issue_projection_clarification(graph=..., projection_id=..., text=..., classification="unchanged-meaning", reason=...)`. Record the returned projection through `clarify-projection` with its operation receipt. This appends the exact newly presented wording and its digests to `clarifications` while retaining the approved `presentation`. The classification is a coordinator attestation, recorded as `coordinator-attestation`. Equal source digests establish unchanged canonical records. They do not establish semantic equivalence of the new prose. Existing confirmation stays bound to the retained approved wording, and canonical approvals, audit freshness, and Design joins remain current. Material corrections update canonical meaning and follow regeneration and confirmation.

Every mutation uses a short identity lock, expected-revision compare-and-swap, strict validation, atomic synchronized replacement, and at most one previous valid generation. Refuse unsafe permissions, symlinks, non-regular or ambiguous state, duplicate or substituted identity, unsupported schemas, and stale receipts. Recover only an unambiguous valid generation. Pause preserves state. Resume revalidates it. Discard requires explicit user authority and claims no success. Workers never write canonical state: they return receipts bound to workflow ID, graph revision, node, branch, commit, and evidence. Reapply only demonstrably disjoint stale updates. Competing semantic updates require reconciliation and user input only when incompatible intent remains.

Readiness requires every outcome and constraint to have grounded work and planned proof, every material decision to be supported and currently confirmed, complete acyclic dependencies and joins, credible ownership and concurrency, a reproducible eligible baseline, and no relevant stale, unresolved, conflicting, or awaiting-user state.

## Implementation, proof, and Git execution contract

The complete graph is the detailed implementation and proof design. It records observable acceptance criteria, positive and negative behavior, verification intent, relevant test surfaces and commands, and test work, while planning itself writes no code or tests and never marks an unexecuted obligation proven. Later evidence must identify the executed command, result, and exact repository revision. Relevant changes stale prior evidence. Revise never-executed proof obligations through `refresh-proof-plan` only, retaining monotonic `execution_required` on any obligation that has executed. Reconfirm only materially changed user decisions.

The graph records later Git execution without performing it. The non-protected workflow branch remains the live integration target. Serial work may later commit directly there. Concurrent writing lanes may later use external worktrees created from exact accepted target commits. One writer owns each lane, shared interfaces are stabilized before fan-out, and a coordinator serializes incremental target-side integration. The graph records the gates under which a later authorized phase may verify a clean accepted lane, remove its worktree, and safely delete only a branch that is committed-to-target and accepted-on-target. Dirty, failing, unmerged, unknown, or still-needed state is preserved. Future executors revalidate the exact repository revision and all parallel-safety claims.

## Stop and downstream boundary

On standalone success, say concisely that the plan is ready, summarize its high-level execution shape, material protections, proof intent, and workflow branch in human terms, and disclose honest non-blocking risks. Name the workflow branch, the baseline commit, and the confirmed material decisions so a later phase continues from that summary plus the graph with no re-asking. Keep the private graph for later direct phases or `use-expskill`. Emit no typed handoff and do not begin implementation.

A later authorized lifecycle, not `$plan`, may push after the first coherent implementation commit, open a draft request against a protected destination, and bind checks to its exact head. It may reach `ready-for-human-review` only after planned work, review findings, independent verification, target and join proof, required checks, and lane cleanup are current. At that terminal gate the helper emits a durable receipt and deletes owned graph generations. AI must never approve, merge, enable auto-merge, or enter a merge queue. Manual review and merge remain outside observable AI control.
